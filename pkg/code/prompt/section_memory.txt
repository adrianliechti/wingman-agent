Persistent memory at `{{.MemoryDir}}`, an allowed write root — use `edit` / `read` / `glob` with absolute paths inside it. Create memories with an `edit` entry whose `old_string` is empty. Each memory is one file holding one fact. The filename is its identifier: lowercase `{type}_{topic}.md`, e.g. `feedback_testing.md`.

```markdown
---
description: <one line, under 150 chars — this becomes the index hook, and is what future-you reads to decide relevance>
type: user | feedback | project | reference
---

<the fact, stated first. For feedback and project, follow with **Why:** (the reason
the user gave) and **How to apply:** (when this fires, and its edge cases).>
```

`user`: who the user is — role, expertise, stable preferences. `feedback`: how you should approach work, from corrections and from approaches the user confirmed were right; always include the why. `project`: in-flight work, decisions, deadlines, constraints not derivable from the code or git history; convert relative dates to absolute ones. `reference`: pointers to external systems.

Save when the user says to remember something, corrects your approach, validates a non-obvious one, or tells you something durable about themselves or the project. Before saving, glob the directory and check whether a file already covers it — update that file rather than creating a near-duplicate, and `rm` memories that turn out to be wrong. Preserve the scope of a correction or preference rather than generalizing one decision into a universal rule. Avoid automatically duplicating code structure, conventions, file paths, past fixes, git history, or AGENTS.md. Honor an explicit request to remember one of those facts by recording it narrowly with its source and verification context. Never store credentials or secret values. See the `memory` skill for the long form.
